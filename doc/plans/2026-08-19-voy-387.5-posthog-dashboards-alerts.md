## Overview

## 1. Dashboards

### 1.1 Executive Overview

Purpose: High-level health snapshot for CEO/CTO. Top-level metrics and trend lines.

**Panels (insights):**
1. **Daily Active Signups** — `auth.signup_completed` count, daily bar chart, last 14 days
2. **Session Start Rate** — `auth.session_started` count, daily area chart, last 14 days
3. **Approval Activity** — `approval.approved` + `approval.rejected` combined count, stacked bar chart by type, last 14 days
4. **Notification Digest Volume** — `notification.digest.sent` count, daily line chart, last 7 days
5. **Error Rate** — `$exception` count, daily line chart, last 7 days, colored red above threshold (see Alerts)
6. **Key Metric Summary** — Bold numbers widget (or table insight):
   - Total signups (last 7 days)
   - Daily active sessions (avg last 7 days)
   - Approval rate (approved / (approved+rejected) %)
   - Error events (last 24h)

**Layout:** 3×2 grid. Summary row at top, trend charts below.

### 1.2 Conversion Funnel

Purpose: Track user journey from signup to activation to engagement.

**Panels (insights):**
1. **Signup → Session Funnel** — Steps: `auth.signup_completed` → `auth.session_started` (within 24h). Funnel visualization. Last 30 days.
2. **Signup → First Approval** — Steps: `auth.signup_completed` → first `approval.approved` (any type) by same user. Funnel visualization. Last 30 days. (NOTE: requires distinctId to match user across events — uses user.id; confirm data model.)
3. **Weekly Conversion Rate** — Conversion rate (sessions / signups) by week. Bar chart. Last 8 weeks.
4. **Signup by Login Method** — Pie chart: `auth.signup_completed` segmented by `login_method` property. Last 30 days.

**Layout:** 2×2 grid. Funnels top, charts below.

### 1.3 Engagement

Purpose: Monitor system usage patterns and approval workflow activity (for COO/operations).

**Panels (insights):**
1. **Daily Approval Events** — `approval.approved` + `approval.rejected` stacked by `approvalType`, daily, last 30 days
2. **Approval Rate** — `approval.approved` / (`approval.approved` + `approval.rejected`) ratio, daily line chart, last 30 days
3. **Rejection Trend** — `approval.rejected` count by day, line chart, last 30 days
4. **Notification Digest Delivery** — `notification.digest.sent` by `frequency` (daily vs hourly), daily bar, last 14 days
5. **High-Activity Companies** — `approval.approved` count by `companyId` (top 10), horizontal bar, last 7 days. (NOTE: companyId is a UUID — consider adding a human-readable label via PostHog person/groups.)

**Layout:** 3×2 grid. Core approval metrics left column, notification + company detail right.

### 1.4 Revenue

Purpose: Track billing/metrics events as proxy for revenue activity. (PostHog events for billing actions should be added in a future phase — currently placeholder.)

**Panels (insights):**
1. **Active Companies** — Companies with any event in last 7 days. Trend line, daily, last 30 days.
2. **Signup Growth** — Cumulative `auth.signup_completed`, line chart, last 30 days
3. **Approval Volume** — `approval.approved` count as activity proxy, daily, last 30 days
4. **Error Impact** — `$exception` events per company (top N), to identify companies experiencing issues. Bar chart, last 7 days.

**Layout:** 2×2 grid.

### 1.5 Acquisition

Purpose: Marketing / product team view of signup and activation channels.

**Panels (insights):**
1. **Signups by Login Method** — `auth.signup_completed` segmented by `login_method`, daily stacked bar, last 30 days
2. **Session Start Rate by Login Method** — `auth.session_started` segmented by login method, daily, last 30 days
3. **Signup Retention** — Users who signed up in a given week and returned (any session) in subsequent weeks. Weekly cohort analysis table.
4. **Active Users per Day** — Distinct `auth.session_started` distinctId count, daily, last 30 days

**Layout:** 2×2 grid. Top row: signup/channel mix. Bottom row: retention + active users.

## 2. Funnels

Create 4 funnels as standalone insights (can be added to dashboards as needed):

### 2.1 Funnel A: Signup → Activation
- **Steps:**
  1. `auth.signup_completed`
  2. `auth.session_started` (within 24h of step 1)
- **Filters:** None (all users)
- **Date range:** Last 30 days, rolling
- **Goal:** Track conversion from signup to at least one session

### 2.2 Funnel B: Signup → First Approval
- **Steps:**
  1. `auth.signup_completed`
  2. `approval.approved` (first occurrence per user)
- **Filters:** Same user (distinctId match across events)
- **Date range:** Last 30 days, rolling
- **Goal:** Track what fraction of signups lead to an approved action (proxy for activation)

### 2.3 Funnel C: Notification Digest Engagement
- **Steps:**
  1. `notification.digest.sent`
  2. `auth.session_started` (within 1h of digest — proxy for notification-driven return)
- **Filters:** Same companyId
- **Date range:** Last 14 days, rolling
- **Goal:** Measure notification effectiveness at driving re-engagement

### 2.4 Funnel D: Approval Workflow Completion
- **Steps:**
  1. `approval.approved` or `approval.rejected` (start of workflow)
  2. `approval.approved` (successful resolution)
- **Filters:** Same approvalId
- **Date range:** Last 30 days, rolling
- **Goal:** Track multi-step approval completion rate (when approvals form chains)

## 3. Alert Rules

Configure alerts in PostHog for operational signals. All alerts should target the team's notification channel (configure in PostHog project settings).

### 3.1 Error Rate Spike
- **Insight:** Daily `$exception` count
- **Condition:** Value > 50 in a single day (threshold)
- **Check interval:** Daily
- **Severity:** Critical
- **Recipients:** #engineering-ops channel (PostHog notification destination)
- **Rationale:** Error spikes indicate a regression or infrastructure issue

### 3.2 Signup Drop-Off
- **Funnel:** Funnel A (Signup → Activation)
- **Condition:** Conversion rate < 60% (baseline expected: ~70-80%)
- **Check interval:** Daily
- **Severity:** High
- **Rationale:** A drop in signup-to-session conversion suggests auth or onboarding issues

### 3.3 Approval Pipeline Stall
- **Insight:** `approval.approved` count
- **Condition:** Zero approval events in any 24-hour window
- **Check interval:** Hourly
- **Severity:** High
- **Rationale:** Zero approvals means agents are blocked — could indicate a system-level failure

### 3.4 Notification Digest Drop
- **Insight:** `notification.digest.sent` count
- **Condition:** < 10 digests/day (baseline expected: varies by company count; tune after 7 days of data)
- **Check interval:** Daily
- **Severity:** Medium
- **Rationale:** Missing digests suggest notification service degradation

## 4. Implementation Notes

### Option A: PostHog API (Recommended for repeatability)
Use the PostHog Management API to create resources programmatically:
- **Dashboard:** `POST /api/projects/{project_id}/dashboards/`
- **Insight:** `POST /api/projects/{project_id}/insights/` (funnels use `funnels` insight type)
- **Alert:** `POST /api/projects/{project_id}/alerts/`

A script can be created at `scripts/posthog-provision-dashboards.sh` (similar to `scripts/posthog-error-monitor.sh`) that takes the POSTHOG_PERSONAL_API_KEY and POSTHOG_PROJECT_ID as env vars and provisions all resources idempotently.

### Option B: PostHog UI (If API access restricted)
Follow the dashboard/funnel/alert specifications above and create manually in the PostHog web interface. Estimated time: ~60 minutes for a PostHog-experienced operator.

### Idempotency
- Dashboard titles serve as natural idempotency keys — skip creation if a dashboard with the matching title exists
- Insights and alerts within each dashboard should be matched by name
