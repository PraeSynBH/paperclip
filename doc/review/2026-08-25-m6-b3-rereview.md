## What I verified (live)

### 1. The committed fix is now correct
- `06ea87e` + `8fb4d72` set `certresolver=mytlschallenge` in `docker-compose.voyonder.yml` and `docker-compose.production.yml`.
- Production Traefik (vps-1, v2.11.42) defines ONLY `mytlschallenge`:
  `--certificatesresolvers.mytlschallenge.acme.tlschallenge=true`
- The narrow PathPrefix rule in `8fb4d72` matches the app's real routes:
  `/api/health`, `/api/auth`, `/api/billing`, `/api/onboarding` (all under `/api`) plus
  `/background-jobs`, `/research`, `/exports` (mounted at ROOT in `server/src/app.ts:140-151` — correctly NOT under `/api`).
  This is actually the correct route map for the standalone voyonder app. Good.

### 2. But production is NOT running that config
- Running `voyonder_api` container (created 2026-08-24T23:55:27Z) has labels:
  `rule=Host(voyonder.com) && (narrow paths)` + `tls.certresolver=letsencrypt`
- Deploy source `/root/voyonder-build/docker-compose.voyonder.yml` (mtime 23:54:43Z) has `letsencrypt`.
- The container was created BEFORE `24bc51d` (00:01:41Z) and `8fb4d72` (00:05:01Z). The deploy at 23:54–23:55 copied the **dirty working tree** (letsencrypt + narrow rule + curl healthcheck), not committed state.
- `24bc51d` even re-introduced `letsencrypt` with a comment claiming it was "per Staff Engineer review" — that is a misreading. My review said `mytlschallenge`. `8fb4d72` corrected it, but only in git.

### 3. Traefik is still erroring on the deployed router
- `docker logs traefik` at 00:07:38Z (after the 23:55 deploy):
  `level=error msg="Router voyonder-api@docker uses a nonexistent resolver: letsencrypt"`
- The routers API lists the router as "enabled" with `letsencrypt`, but Traefik is logging the rejection error continuously.

### 4. `/api/health` = 200 is a false positive caused by a stale cert
- Public `https://voyonder.com/api/health` → 200 with valid LE cert `CN=voyonder.com`
  (`notBefore Jul 27 2026`, `notAfter Oct 25 2026`).
- That cert was issued Jul 27 — it predates all of this work and sits in the ACME store
  (`/letsencrypt/acme.json` contains `voyonder.com` + `www.voyonder.com`).
- Traefik serves the stored cert even though the router references a nonexistent resolver.
  When that cert expires (Oct 25) or Traefik restarts/re-evaluates the docker provider, the
  router with the bad resolver will be rejected → M6 goes dark again. This is "works by luck", not a fix.

### 5. Frontend is now completely down (regression from my first review)
- `voyonder.com/` → 404, `/app` → 404, `/signup` → 404, `/onboarding` → 404.
- At 00:02Z the `travel_app` container was up (9 min) with a `travel_app@docker` router
  (`Host(voyonder.com) && PathPrefix(/api)` → `travel_app:3101`).
- By 00:17Z `travel_app` was GONE from `docker ps` and the `travel_app@docker` router was gone from the table.
- My first review explicitly required: "the /api router must not be the only thing present;
  the travel-planner routers (Host(voyonder.com) → travel_app:3000) must be restored or M6 ships with the frontend down."
  It is now MORE down than before.

### 6. Deploy provenance is broken (root cause)
- `/root/voyonder-build` is NOT a git repository. Deploys copy a dirty working tree, so deployed
  config cannot be traced to a commit. This is how the rejected `letsencrypt` config got back onto the box
  after `06ea87e` had fixed it in git.
